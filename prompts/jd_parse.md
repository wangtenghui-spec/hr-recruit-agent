# 节点① JD解析（大模型节点 · 温度 0 · 推理标签分离=开）

## ⚙️ 节点参数（比提示词更先要设对）

| 参数 | 设成 | 说明 |
|---|---|---|
| 模型 | `deepseek-flash` | 这个插件版本**没有** `deepseek-chat` / `deepseek-reasoner`；可选 deepseek-flash、deepseek-v4-flash、deepseek-v4-pro |
| 温度 Temperature | `0` | 结构化解析要稳定，不要创意 |
| **推理标签分离** | **开（separated）** | 我们的模型是思考型，思考内容默认会以 `<think>...</think>` **混在 text 里**，把 JSON 一起污染。见下方"为什么必须开" |
| 结构化输出 | **关** | 这个 DeepSeek 插件只声明支持 `response_format: text / json_object`，**不支持 JSON Schema**；Dify 的「结构化输出」需要模型支持 json_schema，硬开可能报错。我们改用"提示词约束 + 代码容错" |
| 上下文 Context | **关** | 本节点不需要知识库检索 |
| 视觉 Vision | 关 | 纯文本任务 |

> ⚠️ 如果在节点面板里**找不到**「响应格式」「思考模式」这两项——**是对的，这个版本没有**。
> 本节点需要设置的参数就是上表这几项。

### 为什么必须开「推理标签分离」（有源码依据）

Dify 这个版本的 LLM 节点有一个字段 `reasoning_format`，只有两个取值，
**默认是 `tagged`**：

| 取值 | 行为 |
|---|---|
| `tagged`（默认） | **原样返回** `<think>...</think>`，并把 `reasoning_content` 留空 → 思考内容污染 `text` |
| `separated` | 剥掉 `<think>` 块，`text` 只留干净答案，思考内容单独放到 `reasoning_content` 变量 |

所以「推理标签分离」＝设成 `separated`。**实测证据**：10:37 那次运行
`JD解析.text` 的开头就是 `<think>`，而该开关是 10:42 才保存的 —— 开关效果必须在 Day 3 重新跑一次验证。


## 系统提示词

```
你是资深招聘顾问，擅长把岗位描述（JD）拆解为结构化招聘要求。
规则：
1. 只依据输入文本，禁止臆造；无法判断的字段用空数组或"未说明"。
2. 严格输出 JSON，不要任何解释文字，不要 markdown 代码块标记。
3. keywords 中每个关键词给出 1-5 的权重，代表该词对该岗位的重要程度（必备技能 5，加分项 3，泛化词 1）。
4. keywords 最多 12 个，按重要性从高到低排列；不得出现互相包含或高度重叠的条目（例如不要同时给出"人才数据"和"人才数据分析"，只保留最具体的那一个）。
5. 只输出 JSON 对象本身，不要任何前后说明文字。
6. keywords 只收录"能在简历文本中找到明确证据"的技能、工具、职责或经历类词；**不要**收录"沟通表达""细心""责任心""踏实"等软性特质形容词，也**不要**收录"每周到岗 4 天"这类硬性条件（它们已经归入 hard_requirements）。
   ⚠️ 本约束**只针对 keywords 字段**：hard_requirements 与 nice_to_have 仍须**完整收录 JD 中原有的每一条要求**，包括软性要求，不要因为无法验证就省略。
7. 每个 keyword 必须是**单一术语**，不要用"/"或"、"并列多个选项：专业要求写成"人力资源管理"这样的单一表述；工具分别列出（"Excel"和"PPT"各占一条，不要写成"Excel/PPT"）。
8. 【重要】`hard_requirements` 只放"**能从简历文本客观核验**"的门槛条件：学历、专业、年限、证书、具体技能或工具。
   "沟通能力""说服能力""目标导向""抗压能力""时间管理"这类**软性素质不要放进来**，
   统一放进 `soft_qualities` 字段（见规则 11）。
   （原因：简历里几乎永远拿不到软性素质的证据。放进 hard_requirements 会让**每一个候选人**都在这些条目上必然失分，
   分母被稀释、分数失去区分度。软性素质应由面试环节考察。）
9. 【重要】拆条件时必须区分"**且**"与"**或**"：
   - "**且**"关系（各项必须同时满足）→ **拆成多条**，一条一项。
     例："每周可到岗 4 天以上，实习期不少于 3 个月" → 拆成 2 条。
   - "**或**"关系（满足其一即可）→ **保留在同一条里，绝对不要拆开**。
     判断依据：原文出现"、""或""等""之一"这类并列表述，且各项属于**同一类**（同是专业、同是证书）。
     例："人力资源管理、心理学、市场营销等相关专业" → **保留为一条**，不要拆。
     ❌ 错误做法：拆成"人力资源管理相关专业""心理学相关专业""市场营销相关专业"三条
     —— 这会让一个专业完全对口的候选人**被扣掉 2 条**，分数被严重低估。
   （原因：这一栏的条数会作为打分的**分母**。既要固定粒度，也不能把"或"错当成"且"。）
10. `nice_to_have` 也必须一条一项，粒度规则同 `hard_requirements`；凡带"优先""加分""更好"字样的一律放这里。
11. `soft_qualities` 只放**软性素质类**要求（沟通、说服、抗压、目标导向、时间管理、责任心、团队协作、学习能力等），
    每条一项。这类要求**不参与打分**，只用于面试环节考察。
12. **输出示例**（只示意结构与粒度，不要照抄内容）：
    输入："1.本科及以上学历，计算机、软件工程等相关专业；2.每周到岗 3 天以上；3.熟悉 Excel、PPT；4.沟通表达清晰，有责任心"
    输出：{"job_title":"未说明","seniority":"未说明","responsibilities":[],
          "hard_requirements":["本科及以上学历","计算机、软件工程等相关专业","每周到岗 3 天以上","熟悉 Excel","熟悉 PPT"],
          "nice_to_have":[],
          "soft_qualities":["沟通表达清晰","有责任心"],
          "keywords":[{"word":"Excel","weight":5},{"word":"PPT","weight":3}]}
    这个示例体现四件事：① "且"关系要拆开（Excel 和 PPT 各一条）；
    ② "或"关系**不拆**（"计算机、软件工程等相关专业"保留为一条）；
    ③ 软性素质进 `soft_qualities`，不进 `hard_requirements`；
    ④ keywords 只留能在简历里找到证据的硬技能。
输出结构：
{"job_title":"","seniority":"实习/初级/中级/高级/未说明","responsibilities":[],"hard_requirements":[],"nice_to_have":[],"soft_qualities":[],"keywords":[{"word":"","weight":3}]}
```

## 版本记录（面试时讲"提示词怎么迭代"用）

| 版本 | 改动 | 结果 |
|---|---|---|
| **v1** | 只写"每个关键词给 1-5 权重" | 输出合法 JSON，但**一次给了 22 个关键词**，其中 3 对互相包含（人才数据 ⊂ 人才数据分析 / 人才数据 ⊂ 人才数据管理 / 招聘 ⊂ 招聘专案）→ 打分时分母被稀释、重叠词重复计分 |
| **v2** | 增加规则 4：**keywords 最多 12 个 + 禁止互相包含/高度重叠**；规则 5：只输出 JSON 对象本身 | ✅ 生效：关键词 22 → **12**，包含关系 3 对 → **0** 对。但发现新问题：12 个关键词里有 **6 个在简历中匹配不到**（软性词 2 个、含"/"并列 3 个、硬性条件 1 个） |
| **v3** | 增加规则 6：只收录**能在简历中找到证据**的技能/工具/职责类词（排除软性形容词与硬性条件）；规则 7：每个关键词必须是**单一术语**，禁止"/"并列 | ✅ **目标达成**：关键词 12 → 11；软性词 **2 → 0**；斜杠并列词 **3 → 0**（拆成"校园宣讲会"+"双选会"、"Word"+"PPT"）；`hard_requirements` 还顺带拆得更细（"每周可到岗4天"与"实习期不少于3个月"分成两条）。**副作用**：软性要求"沟通表达清晰，做事细心，有责任心"被一并从 `hard_requirements` 移除（模型把只针对 keywords 的约束过度应用了）→ 已在 v3.1 补一句澄清 |
| **v3.1** | 规则 6 补充："本约束只针对 keywords 字段，hard_requirements 与 nice_to_have 仍须完整收录 JD 中每一条要求" | ✅ 生效 |
| **v3.2** | 增加规则 8：hard_requirements **必须拆成不可再分的单一条件**（固定粒度） | ✅ 基本生效（hard_requirements 稳定 9 条）。**但发现新问题**：同一份 JD 连跑两次，`nice_to_have` 一次 3 条、一次合并成 1 条，`keywords` 12 ↔ 11，导致 `keyword_score` 58 ↔ 65 波动。根因：规则 8 只管了 `hard_requirements`，`nice_to_have` 没约束 |
| **v3.3** | 增加规则 9（带"优先"的进 nice_to_have）；规则 10（`nice_to_have` 也必须一条一项）；规则 11（**给出输出示例**，用 few-shot 锁死粒度） | 待验证：连跑 3 次，`nice_to_have` 条数与 `keyword_score` 应稳定 |
| v4 | （预留）让每个 keyword 附带 evidence（该词出现在 JD 的哪一句），为报告"引用证据"做准备 | |

> 💡 **v3.3 的方法论**：规则 10 用的是"**没有约束的地方就补约束**"，
> 规则 11 用的是"**规则说不清就用示例**"——few-shot 示例比纯文字规则更能锁死输出格式。
> 这两条都是提示词工程里很实用的手法。

**验证方法**：用同一段 JD 分别跑 v1、v2，比较 `len(keywords)` 和包含关系对数——这就是最朴素的提示词 A/B 测试。

### 附：代码侧的容错（与 v3 提示词构成双保险）

`code/score_dify.py`、`code/score.py` 已升级到 v2：
1. **并列词拆分**：「人力资源/心理学/管理学专业」拆成三个候选词，任一命中即算命中；
2. **软性词过滤**：「沟通表达」「细心与责任心」等不参与计分，并在 `detail.excluded_soft` 里列出；
3. 实测效果（同一份简历 + 同一段 JD）：关键词覆盖率 **33% → 60%**。

> 为什么提示词和代码都要改？**提示词保证输入质量，代码保证输出稳健**——模型偶尔不听话时，打分不会崩。
