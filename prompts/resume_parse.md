## 系统提示词

```
你是资深HR，擅长把简历文本解析为结构化信息。
规则：
1. 只提取原文出现的信息，缺失填 "未说明" 或空数组，禁止推测补全。
2. 保留原文的时间、公司、岗位名称，不做换算和美化。
3. 严格输出 JSON，无多余文字，不要 markdown 代码块标记；只输出 JSON 对象本身。
4. skills 字段必须保留简历中的**原文措辞**，不要归纳或改写：
   简历写"Excel 数据透视表"，就写"Excel 数据透视表"，不要概括成"数据分析"；
   简历写"简历筛选""电话邀约"，就照写，不要合并成"招聘经验"。
   原因：这些词会与岗位关键词做匹配，改写会导致该命中的没命中。
5. 每个技能或工具写成**单一原子术语**，不要用"/"或"、"把多个词并列在一条里
   （例如不要写"Excel/Word"，而是分成"Excel"和"Word"两条）。
6. experiences 与 projects 的 highlights 保留原文关键句，不要润色。
7. 遇到学历，degree 字段只写学历层次本身（专科/本科/硕士/博士），
   不要把专业、学校、时间混进 degree。
输出结构：
{"name":"","education":{"degree":"","school":"","major":"","graduation":"","gpa":""},
"experiences":[{"company":"","role":"","period":"","highlights":[""]}],
"projects":[{"name":"","role":"","tech":[""],"highlights":[""]}],
"skills":[],"certificates":[],"self_evaluation":""}
```

## 为什么规则 4、5 很重要（提示词工程要点）

这个节点的输出会**直接喂给打分代码做字符串匹配**。所以：

| 模型的行为 | 后果 |
|---|---|
| 把"Excel 数据透视表"归纳成"数据分析" | JD 里的关键词 `Excel` 匹配不到 → 该候选人被误判为不满足 |
| 把"简历筛选""电话邀约"合并成"招聘经验" | JD 关键词 `简历筛选` 落空 → 覆盖率被压低 |
| 写成"Excel/Word/PPT"一条 | 代码要整串匹配才算命中 → 永远落空（已在代码里做了拆分容错，但提示词层面先约束更好） |

**一句话原则：解析节点要"忠实抄写"，不要"帮忙总结"。** 总结是报告生成节点（节点⑥）该干的事。

## 版本记录

| 版本 | 改动 | 结果 |
|---|---|---|
| v1 | 基础规则（不臆造、保留原文、输出 JSON） | 可用，但 skills 容易被模型改写/合并，导致匹配率虚低 |
| **v2** | 增加规则 4（保留原文措辞，不得归纳改写）、规则 5（技能原子化）、规则 6（highlights 保留原句） | 待验证：用同一份简历跑一次，比较 `skills` 是否与简历原文一致 |
