# 节点③ 硬性要求判断（大模型节点 · 温度 0 · 输出 JSON）

> **为什么需要这个节点**：Day 2 实测发现，用字符串匹配判断硬性要求会有两个问题——
> 1. **语义包含判不出**：简历写"本科"，JD 要求"大专及以上在读" → 字符串匹配判为**未命中**（错误）
> 2. **分母不稳定**：JD 解析把并列条件合并/拆开，条数在 4~7 之间跳，导致 hard_score 从 50% 掉到 29%
>
> 这个节点把"是否符合"交给模型做语义判断，同时**只按 JD 原文的条目**逐条判断，分母由 JD 决定，不受缓存波动影响。

## 系统提示词

```
你是严谨的招聘初筛助手，负责判断候选人是否满足岗位的每一条硬性要求。

规则：
1. 逐条判断，不遗漏、不增加条目：只能输出输入的 hard_requirements 数组中给出的要求，不要自行补充新要求。
2. 判断要基于简历原文证据，允许语义等价与包含关系：
   - "本科" 满足 "大专及以上"；"硕士" 也满足 "大专及以上"；
   - "本科学历" 与 "本科" 视为同一含义；
   - "3 年招聘经验" 满足 "2 年以上经验"；
   - 简历未提及该要求时，判为 false，不要猜测。
3. 【最重要】区分"过去经历"与"未来可投入时间"，两者的判断依据完全不同：
   - 写"每周可到岗 X 天以上""实习期不少于 X 个月""可连续实习到 X 月""能接受出差/加班"这类条件，
     问的是候选人**未来能投入多少时间**。**不能**用简历里过去某段实习的时长来充当答案。
     简历没说明未来可投入多久，就判 false，evidence 写"简历未提及可实习时长/可到岗天数"。
   - 写"具备 X 年以上相关经验""有 X 年招聘经验"这类条件，问的是**过去的经历长度**，
     这时才用简历里的实习/工作起止时间来计算。
   - 例：JD 要求"实习期不少于 3 个月"，简历写过去在某公司实习 2025.07-2025.09（共 3 个月），
     但没写未来还能实习多久 → 判 **false**（过去做过 3 个月 ≠ 未来能再做 3 个月）。
4. 【最重要·防造假】判断必须基于**经历描述里的证据**，但要区分两类要求，不能一刀切：
   （a）**专业能力类**（有实质门槛、容易被夸大）：如 "cold call""人才寻访""Mapping"
       "RPO""猎头""招聘渠道运营""数据分析""人才地图"……
       这类**必须有实习或项目经历里的动作佐证**。只在技能清单里出现、经历中无相关动作
       → 判 **false**，evidence 写"仅技能清单声明，经历中无佐证"。
   （b）**通识工具类**（几乎人人都会、简历里通常也不会专门描述怎么用）：
       如 "熟练使用 Word / Excel / PPT / Office"、"持有 CET-4 / CET-6"、"会用微信、钉钉"……
       只要技能清单或证书栏里**明确列出**，**可以判 true**。
       **例外**：如果整份简历的经历描述极其单薄（例如实习经历只有一句"完成领导交办的其他工作"），
       说明候选人没有可核验的实操，这时连通识工具也判 **false**。
   例①：技能栏列了"cold call、RPO、猎头"，但实习只有一个月、描述是"完成领导交办的其他工作"
        → "熟悉主流招聘渠道的操作" 判 **false**；
        同一份简历里的 Word/PPT 因为经历整体单薄，也判 **false**。
   例②：简历有 2 段详细实习（写清了做了什么、做了多少），技能栏列了 Word/PPT 但经历里没专门提
        → "熟练使用 Word""熟练使用 PPT" 判 **true**（通识工具，清单声明足够，不能因此误伤）。
   判断口诀：**专业能力看经历，通识工具看清单；经历整体单薄则一律从严。**
5. satisfied 只能是 true / false 两种取值，不要写成字符串，也不要写"部分满足"。
6. evidence 必须引用简历原文中的具体片段（**优先引用经历描述**）；简历未提及时写 "简历未提及"。
7. reason 用一句话说明判断理由（尤其是判 true 时的包含关系）。
8. 严格输出 JSON，不要任何解释文字，不要 markdown 代码块标记。
输出结构：
{"items":[{"requirement":"","satisfied":true,"evidence":"","reason":""}]}
```

## 与打分代码的衔接

这个节点的输出（`text`）接到**代码节点的第三个输入 `hard_check_json`**：

```
代码节点的输入变量：
  jd_json         ← JD解析 / text
  resume_json     ← 简历解析 / text
  hard_check_json ← 硬性要求判断 / text     ← 新增
```

打分代码（v3）的逻辑：
1. **优先用模型判断**：解析 `hard_check_json`，`hard_score = satisfied 条数 / 总条数`
2. **回退**：如果该输入为空或解析失败（比如这个节点没接、或模型返回异常），自动退回**字符串匹配**，保证流程不中断
3. `detail` 里会输出 `hard_mode`（`model` 或 `string`），便于核对当前用的是哪种模式

> **面试可讲**：我的打分器支持两种硬性要求判定模式——字符串匹配（快、免费、但判不出语义包含）与模型语义判断（准、多一次调用），并把当前模式写进输出明细，做到可追溯、可回退。

## 验证方法（Day 3 必做）

用 `data/resume/cv_01.txt`（写明"本科"）+ `data/jd/jd_01.txt`（要求"大专及以上在读"）跑一次：

- **改之前**（字符串模式）：这条判为**未命中**，`hard_score` 偏低
- **改之后**（模型模式）：这条应判为**命中**，`satisfied: true`，`evidence` 引用"本科"
- 期望 `hard_score` 明显上升，且**同一输入连跑两次数值一致**

### 预期数值（本机用真实数据实测）

| 指标 | 字符串模式（旧） | 语义判断模式（新） | 变化 |
|---|---|---|---|
| `hard_score` | **50** | **90** | **+40** |
| 总分 | **63** | **83** | **+20** |
| 档位 | 待定（边界情况，建议人工复核） | **推荐进入面试** | 跨 2 档 |

字符串模式 10 条里**错 4 条**，全部是"语义等价但字面不同"：

| JD 要求 | 代码候选词 | 结果 | 正解 |
|---|---|---|---|
| 大专及以上在读 | `['大专及以上在读']` | ❌ | 简历"本科" → 应命中 |
| 人力资源相关专业 | `['人力资源相关专业']` | ❌ | 简历"人力资源管理" → 应命中 |
| 实习期不少于 3 个月 | `['实习期不少于', '个月']` | ❌ | 简历"2025.07-2025.09" → 应命中 |
| 做事细心 | `['做事细心']` | ❌ | 简历"细心" → 应命中 |

> **一句话总结（面试用）**：字符串匹配的天花板是"字面相同"，而招聘判断需要的是"语义等价"。
> 这不是代码 bug，是**方法的固有局限**——所以我把判断权交给模型，同时保留字符串匹配做兜底。

## v4 更新：修掉"同一条要求两次判断结果不同"

### 现象（真实数据，不是假设）

接上节点后连跑两次，**9 条要求里 8 条判断一致，只有 1 条翻转**：

| JD 要求 | 第 1 次 | 第 2 次 |
|---|---|---|
| 实习期不少于 3 个月 | `true`　evidence：某公司实习 2025.07-2025.09，持续 3 个月 | `false`　evidence：简历未说明可实习期时长 |

`hard_score` 因此从 89 掉到 78，总分 82 → 78。

### 根因不是"模型随机"，而是**要求本身有歧义**

JD 原文是：
```
任职要求：
1.大专及以上在读，人力资源、心理学、管理学相关专业优先；
2.每周可到岗 4 天以上，实习期不少于 3 个月；
```

「实习期不少于 3 个月」和「每周可到岗 4 天以上」**并列**，说明它是一条
**对候选人未来可投入时间的要求**（入职后能干多久），
不是"你过去实习过多久"。

而简历里那段 `2025.07-2025.09` 是**过去的实习经历**。
所以：

- ❌ 第 1 次的判断错了：**拿过去的时长当未来的承诺**
- ✅ 第 2 次的判断对了：过去做过 3 个月 ≠ 未来还能再做 3 个月

### 修法：把判断口径写进提示词（规则 3）

见上方系统提示词的**规则 3**：明确区分两类条件——
「未来可投入时间」（用简历中对该承诺的说明判断，没说就 false）
与「过去经历长度」（才用起止时间计算）。

> 💡 **这是本次项目里最值得讲的一个发现**：
> 表面看是"模型不稳定"，追下去发现是**需求语义有歧义**，
> 而模型两次各选了一种合理解释。
> **所以提升确定性的正确做法不是调温度，而是消除歧义**——
> 温度只会让随机性变小，不会让歧义消失。
>
> 这也解释了为什么"连跑两次分数一致"必须当成一条**硬性验收标准**：
> 它逼你去追问不一致的根因，而不是用"模型就这样"糊过去。

## ⚠️ 另一处还没解决的波动（Day 4 处理）

`JD解析` 节点的输出**也有粒度波动**，两次运行对比：

| 字段 | 第 1 次 | 第 2 次 |
|---|---|---|
| `nice_to_have` | 3 条（人力资源/心理学/管理学 各一条） | **1 条**（合并成"人力资源、心理学、管理学相关专业优先"） |
| `keywords` 条数 | 12 | **11**（少了"人力资源管理"，多了"招聘周报"） |
| `keyword_score` | 58 | **65** |

这属于规则 7（单一术语）和规则 9（优先项拆分）**执行粒度不稳**。
影响比硬性要求小（`keyword_score` 波动 7 分），但同样会跳档。

**Day 4 的备选做法**（按性价比排序）：
1. 在 `JD解析` 提示词里**给出一个"输出示例"**（few-shot），比纯规则更稳
2. 把 `nice_to_have` 的拆分要求也写成"必须一条一项"，并给反例
3. 代码侧对 `keywords` 做**归一化**：合并语义重复项、限制总条数
4. （不推荐）降低温度——已经是 0 了，没有下调空间
