# HR 招聘助手 Agent

> **输入一份岗位 JD 和一份简历，自动输出一份带评分、证据和面试题的候选人评估报告。**

一个基于 [Dify](https://dify.ai) 工作流搭建的 HR 招聘初筛 AI Agent。
每条结论都附**简历原文证据**，可疑的地方**明确标注出来交人工**，而不是给一个说不清来由的分数。

**技术栈**：Dify（9 节点工作流）· DeepSeek · Python（打分逻辑 + 本地界面）

**实测**：端到端 35~60 秒 ｜ 单次约 1.5~2 万 tokens ｜ 9 节点工作流 ｜ 打分逻辑迭代 7 版

🎬 **演示视频（2 分钟）** <https://www.bilibili.com/video/BV1BwHD68EgB/>

## 一、它解决什么问题

HR 初筛的真实痛点：

| 痛点 | 现状 | 这个项目怎么做 |
|---|---|---|
| **看不过来** | 一个岗位几十上百份简历，逐份看很累 | 一份简历约 35 秒出评估报告 |
| **标准不一致** | 不同人、不同时段判断尺度会漂 | 打分口径固定、可复现 |
| **说了不算数** | 问"为什么给这个分"说不清 | 每条结论附简历原文证据 |
| **不敢信 AI** | 怕它编、怕它黑盒 | 可疑的**明确标注**出来交人工，可疑到一定程度就拒绝评分 |

## 三、核心能力

### 1. 打分可解释——每条结论都带证据

报告里不可能出现"候选人不错"这种没出处的评价。每条命中项后面都跟着**简历原文片段**，
每条未命中项都要写清"该能力在岗位中的用途 + 影响程度"。

> **为什么**：招聘是高风险决策，HR 需要能**独立复核**每一条结论。
> 这是 AI 工具能被信任的前提。

### 2. 硬性要求用**语义判断**，不是字符串匹配

简历写"本科"，JD 要求"大专及以上"——字符串匹配会判**不满足**（因为简历里没有"大专"两个字），
但这是错的。所以硬性要求交给模型逐条做语义判断，并**保留字符串匹配作为兜底**，
在输出里用 `hard_mode` 字段标注当前走的是哪条路径。

> **实测**：同一份简历同一段 JD，字符串匹配给 `hard_score = 14`，语义判断给 `57`。

### 3. 防关键词堆砌——"声称会" ≠ "做过"

这是最容易踩的坑：一份技能栏堆了 32 个词、实习只写了一句"完成领导交办的其他事项"的简历，
如果只做字面匹配，能拿到 **72 分「推荐进入面试」**。

所以把简历拆成两个**证据区**：

| 区 | 包含 | 含义 | 处理 |
|---|---|---|---|
| **强证据区** | 实习/项目的公司、岗位、highlights | **做过** | 计分 |
| **弱证据区** | 技能清单、证书、自我评价 | **声称会** | **不计分**，单列交人工 |

> **实测**：同一份堆砌简历从 **72 分 → 30 分**，而正常简历几乎不受影响（86 → 88）。

### 4. 知道什么时候"不知道"

输入填错时（比如把文件路径当内容填进了 JD 框），系统**不会**给一个看起来正常的分数，
而是明确返回：

```
score = 0
level = 数据不足，无法评分
risk  = ⚠️ 最常见的原因是把文件路径当内容填进了输入框 …
```

> **为什么重要**：修这条之前，同样的坏输入会得到 **56 分「待定，需人工复核」**——
> 一个**看起来完全正常**的评估结论。
> **静默失败 + 貌似合理的输出，是最危险的一类错误。**

### 5. 输出两种形态

| 形态 | 用途 |
|---|---|
| **Markdown 报告** | 给人看的，六章节固定结构 |
| **结构化字段** | 给机器用的（`score` / `level` / `matched` / `suspect` / `missing` / `detail`） |

## 四、工作流架构

```
                        用户输入
                  （jd_text / resume_text / jd_json_fixed）
                            │
        ┌───────────────────┼───────────────────┐
        ▼                   ▼                   ▼
     JD解析              简历解析          岗位要求路由 ★
        │                   │              （固化值优先，
        └────────┬──────────┘               否则现场解析）
                 ▼
           硬性要求判断          ← 逐条语义判断 + 防造假规则
                 │
                 ▼
             匹配打分            ← 纯 Python 代码节点，5:3:2 加权
                 │
                 ▼
           面试问题生成          ← 缺口验证 / 疑点澄清 / 经历深挖
                 │
                 ▼
             报告生成            ← 只组装不判断，六章节固定结构
                 │
                 ▼
               输出
```

**9 个节点**：3 个解析/判断类 LLM 节点 + 1 个路由代码节点 + 1 个打分代码节点 +
1 个出题 LLM 节点 + 1 个报告 LLM 节点 + 输入/输出。

★ `岗位要求路由` 是解决"分数不可比"问题的关键节点，见[设计取舍 §1](#1-为什么要把岗位要求固化)。

## 五、打分口径

> 这一节是项目的核心。**能说清分数怎么来的，这个系统才可信。**

### 总分

```
score = hard_score × 0.5  +  keyword_score × 0.3  +  experience_score × 0.2
        （硬性要求满足度）    （关键词加权覆盖）      （经历完整度）
```

### 规则 1：关键词三态 + 证据分级

| 状态 | 判据 | 是否计分 |
|---|---|---|
| **命中** | 强证据区有字面命中，或汉字二元组重叠率 ≥ 0.6 | ✅ |
| **仅声明** | 只在弱证据区（技能清单/证书/自评）出现 | ❌ 单列交人工 |
| **未命中** | 两处都没有 | ❌ |

> **汉字二元组容错**解决的是中文动宾倒装：
> JD 写「面试安排」，简历写「协助**安排面试**」——字面匹配必然失败，
> 但二元组 `{面试, 试安, 安排}` 与 `{安排, 排面, 面试}` 重叠 2/3，判定为命中。

### 规则 2：硬性要求只算"能从简历核验的"

| 类型 | 例子 | 处理 |
|---|---|---|
| 可核验的资格门槛 | 学历、专业、年限、证书、技能 | ✅ 计分 |
| **软性素质** | 沟通能力、说服能力、抗压、目标导向、时间管理 | ❌ 不计分，进 `excluded_soft_hard` |
| **意愿 / 可用性** | 每周到岗天数、实习期时长、能否出差 | ❌ 不计分，进 `to_confirm`，报告标"必须在面试中确认" |

> **为什么**：后两类条件**简历里永远拿不到证据**。让它们计分等于给每个候选人都固定扣分——
> 既不公平，也把分数区间压缩了，失去区分度。
>
> **实测**：`jd_01` 的 9 条硬性要求里有 2 条是可用性条件，简历必然"未提及"，
> 白白把 `hard_score` 从 100 压到 78。

### 规则 3：防造假——专业能力看经历，通识工具看清单

| 类型 | 判据 |
|---|---|
| **专业能力**（cold call / 人才寻访 / RPO / Mapping…） | 必须有**经历里**的动作佐证，否则判 false |
| **通识工具**（Word / Excel / PPT / CET-4…） | 技能清单列出即可判 true |
| **例外** | 整份简历经历描述**极其单薄**时，连通识工具也从严 |

### 规则 4：分档 + 边界缓冲

| 分数 | 档位 |
|---|---|
| ≥ 72 | 推荐进入面试 |
| 64 ~ 71 | 推荐进入面试（边界情况，建议人工复核） |
| 52 ~ 63 | 待定，需人工复核 |
| 44 ~ 51 | 待定（边界情况，建议人工复核） |
| < 44 | 暂不推荐 |

> **边界缓冲的作用**：LLM 流水线有 ±2 分的固有波动。
> **不隐藏波动，而是把波动范围内的结果显式标记成"建议人工复核"**，
> 而不是让它静默地跳到另一个档位。

### 规则 5：数据不足时拒绝评分

JD 或简历解析结果为空 → `score = 0`、`level = 数据不足，无法评分`（见[核心能力 §4](#4-知道什么时候不知道)）。

## 六、实测数据

### 端到端性能

| 指标 | 实测值 |
|---|---|
| 单次耗时 | **35 ~ 60 秒**（实测 35.2 / 39.8 / 55.9 秒） |
| 单次 tokens | **15,000 ~ 21,000**（实测 15,110 / 15,905 / 20,721） |
| 节点数 | 9 |
| 报告长度 | 约 4,000 字符（六章节固定结构） |
| 成本大头 | **报告生成节点**（输出 4,000+ tokens 是最贵的部分） |
| 耗时大头 | **面试问题生成节点**（出 6 道带四要素的题最花时间） |

### 测试用例设计

评测集**设计**为 **20 组用例**，覆盖 10 种简历类型（完全匹配 / 技能缺失 / 信息残缺 / 跨专业 /
超长 / 英文 / 关键词堆砌 / 时间线冲突 / 实习不相关 / 同岗不同级）+ 超短 JD（72 字）
与超长 JD（1076 字）两个边界，另含空输入、重复投递、全角半角混排等。

配套数据已就绪：[`data/jd/`](data/jd/) 15 份合成 JD + [`data/resume/`](data/resume/) 10 份合成简历。

> ⚠️ **状态说明（如实标注）**：这 20 组用例的**设计与数据已完备**，
> 但**尚未批量跑完**，因此这里**不列准确率 / 失败率等汇总指标**——
> 没跑完就不给数字，比给一个好看的估计值可靠。
>
> 已经完成的是**针对性实测**（见上一节「关键实测数字」）：
> 每一组都是先发现一个具体问题、再验证修复效果，逐条跑出来的。
>
> 未跑完的用例清单见 [`test/运行清单.csv`](test/运行清单.csv)
> （只登记用例设计与期望行为，**未填分数**——避免把"跑过的"和"没跑的"混在一起）。

### 评测为什么"以行为为主判据"

因为**分数刻度是我们自己定的**——拿自己定的刻度当标准答案，等于自己证明自己。

| 判据类型 | 例子 | 性质 |
|---|---|---|
| **行为型**（主） | "出现关键词堆砌警告"、"证据栏没有编造字段" | **可证伪的客观事实** |
| **分数型**（参考） | "档位不低于待定" | 偏好 |

### 波动治理效果

| | 改造前 | 改造后 |
|---|---|---|
| 同一岗位的关键词表 | **8 次运行 → 8 张不同的表** | 1 张（固化档案） |
| 关键词总权重（打分分母） | **38 ~ 58**（摆 **52%**） | **44（恒定）** |
| 同一候选人 `keyword_score` | **49 ~ 65** | 恒定 |
| 档位标签 | 在"推荐"和"边界情况"之间来回跳 | 稳定 |

## 七、快速开始

### 前置条件

- Docker（跑 Dify 自托管）
- Python 3.10+（只用标准库，不需要装任何第三方包）
- 一个 DeepSeek API Key

### 1. 起 Dify

```bash
cd dify/docker
docker compose up -d
```

然后浏览器打开 <http://localhost/> 完成初始化。

> 本项目用的是 **Dify CE 1.17.1**，15 个容器。
> 部署过程与踩的坑见 [`logs/开发日志.md`](logs/开发日志.md) 阶段 1。

### 2. 导入工作流

在 Dify 里新建一个 **Workflow** 应用，按 [`README-施工说明.md`](README-施工说明.md) 搭 9 个节点。
提示词可以直接从 [`prompts/节点提示词汇总.txt`](prompts/节点提示词汇总.txt) 复制。

### 3. 打开本地界面

```bash
# 标准库版（零依赖）
tools/local_web/启动界面.bat

# 或 Streamlit 版
tools/local_web/启动界面-Streamlit.bat
```

首次运行需要把 Dify 的 API 密钥填进 `tools/local_web/config.json`：

```json
{
  "api_base": "http://localhost/v1",
  "api_key": "app-你的密钥"
}
```

> ⚠️ 密钥不要提交到 Git（`.gitignore` 已经排除了这个文件）。

### 4. 跑测试

```bash
python tests/test_score.py      # 打分逻辑回归测试（30+ 项断言）
python tests/test_router.py     # 固化路由节点（8 项断言）
```

## 八、迭代记录

打分逻辑一共迭代了 7 版。**每一版都是被一个具体的真实问题驱动的**——
这张表比"我写了个 Agent"更能说明问题解决能力。

| 版本 | 改了什么 | 触发它的具体问题 |
|---|---|---|
| v2 | 并列写法容错 + 软性词过滤 | 关键词里混着"沟通表达"这种没法验证的词 |
| v3 | 硬性要求交给模型语义判断，失败回退字符串匹配 | 字符串匹配判不出"本科 满足 大专及以上" |
| v4 | 关键词三态（命中 / 疑似 / 未命中） | 中文动宾倒装：「面试安排」vs「安排面试」漏判 |
| v5 | 软性素质从 `hard_score` 剥离 | 14 条硬性要求里 5 条是软性，分母被稀释 |
| v6 | 意愿/可用性条件改为"面试确认项" | 「每周到岗 4 天」简历里永远不会写，等于给所有人扣分 |
| v7 | 证据分级（强/弱证据区） | **关键词堆砌能刷到 72 分**——"声称会" ≠ "做过" |
| v8 | 数据不足时拒绝评分 | 坏输入会得到 **56 分「待定」**——静默失败 + 貌似合理的输出 |

### 三个"没有报错的 bug"

比上面那些更值得讲的，是这三个——**它们都不报错，只是悄悄给出错误结论**：

| # | 现象 | 真因 |
|---|---|---|
| 1 | 报告里写"上游疑似命中字段为空，但风险里有 5 项，两处不一致" | 报告节点的 `suspect` 变量被粘坏了（截断成 `{{`） |
| 2 | 输入填错，系统给出 56 分「待定」 | 打分代码的 `else 60` 兜底默认值造出了**虚假分数** |
| 3 | 三个输入框填了文件路径，模型返回一堆"未说明" | 文档里"填 `data\jd\jd_01.txt`"有歧义（是填内容还是填路径） |

> **共同点**：系统都在"正常工作"，只是结果错了。
> 我的应对思路是统一的——**要么自动化（不让人做精确操作），要么让系统能识别错误并明确报出来**。

## 九、几个设计取舍

### 1. 为什么要把"岗位要求"固化

**问题**：同一个岗位连跑 8 次，`JD解析` 每次都重新抽签，给出 **8 张不同的关键词表**——
15 个出现过的关键词里只有 8 个稳定，打分分母在 **38 ~ 58** 之间摆。
结果：**候选人 A 用分母 43 量、候选人 B 用分母 40 量，分数不可比。**

**修法**：加一个「岗位要求路由」节点——同一个岗位**解析一次、存成岗位档案、所有候选人复用**。

```
用户输入
  ├─ jd_text        （JD 原文）
  └─ jd_json_fixed  （固化好的岗位档案，可选）
        │
        ▼
      JD解析 ──→ 岗位要求路由 ──┬──→ 硬性要求判断 ──→ 匹配打分
                              └──────────────────→ 匹配打分
```

**为什么这是对的**：**岗位要求是岗位的属性，与候选人无关**。
把它放在每个候选人的执行路径里重新生成，本身就是架构错误。
真实 ATS 系统也是这么做的（JD 录入一次 → 结构化 → 复用）。

**额外收益**：固化前需要**人工审阅**，这就给了修正 LLM 输出的机会。
比如我把 `招聘数据统计` 改成 `招聘数据`（模型把动宾短语倒装了），
并把 `猎头`/`RPO` 从计分关键词里删掉——**它们在 JD 里是"优先"条件，加分项不该让候选人扣分**。

### 2. 为什么关键词"疑似"不计分

如果把二元组重叠的阈值调松直接当命中，`keyword_score` 会上升、总分更好看。
但**我无法保证在其他数据上不产生假阳性**。

所以引入"疑似命中"这个**中间态**：不计入分数，但明确列出供人工确认。
**两个通道同时满足两个目标——分数保持保守，信息不丢失。**

### 3. 为什么用"行为期望"而不是"分数期望"来评测

见[实测数据 §评测为什么以行为为主判据](#评测为什么以行为为主判据)。

### 4. 为什么报告节点"只组装不判断"

分数、命中、缺口、硬性要求是否满足——**全部由上游算好了**，报告节点只负责排版成人话。

**为什么**：如果让报告节点"自己再看一遍简历、自己下结论"，
就会出现**报告结论和 `score` 打架**，而且无法定位是哪一步错了。
**判断只做一次，组装可以多次。**

而且提示词里明确要求：**发现上游数据矛盾时不要自行修正，标注"数据待核实"**。
这条规则在开发过程中**三次**帮我抓到了真 bug。

## 十一、局限与后续

| 局限 | 说明 | 可能的改进 |
|---|---|---|
| **简历侧仍有波动** | 同一份简历解析两次，`skills` 措辞可能略有不同 | 目前影响小；若要做"一份简历投多个岗位"再固化 |
| **档位阈值是初版标定** | 只用 4 个锚点定的（完全匹配 / 资历不足 / 完全无关 / 信息残缺） | 20 组用例跑完后，用真实分布重新校准 |
| **20 组用例尚未跑完** | 用例设计与配套数据已完备，但未批量执行，所以没有汇总指标 | 跑完后补上准确率 / 失败率，并据此调阈值 |
| **成本偏高** | 报告生成节点占 4,000+ tokens | 可对长简历做摘要后再生成 |
| **没有并发/队列** | 一次一个请求 | 生产环境需要加队列和限流 |
| **知识库未接入工作流** | 知识库 `hr-interview-bank` **已建好并完成向量化**（5 篇文档 → 68 个分段，`BAAI/bge-m3`，索引全部 `completed`），但**没有接进工作流**——嵌入服务计费受限。已发布工作流里不存在 `knowledge-retrieval` 节点 | 换一个可用的嵌入服务后，接入 `面试问题生成` 节点，用真实题库约束出题范围 |
