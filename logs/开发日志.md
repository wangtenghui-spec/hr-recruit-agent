## 阶段 1 ｜ 环境与最小链路

**目标**：先让"JD 文本 → 结构化 JSON"这条路能跑通，再谈别的。

- 用 Docker Compose 在本地部署 **Dify CE 1.17.1**（15 个容器，含 Postgres / Redis / Weaviate / Nginx）。
  过程中踩了 WSL 安装、Docker Desktop 启动、容器健康检查三个坑。
- 搭最小工作流：`开始 → JD解析(LLM) → 结束`，验证模型能稳定输出合法 JSON。
- 准备测试数据集：**15 份合成 JD + 10 份合成简历**，
  刻意覆盖超短（72 字）、超长（1076 字）、全英文、关键词堆砌、时间线冲突等边界。
  > 选合成数据而不是真实简历，是为了避免涉及任何真实候选人信息。
- 建立知识库 `hr-interview-bank`：5 篇文档切分为 **68 个分段**，
  使用 `BAAI/bge-m3` 完成向量化入库，索引状态全部 `completed`。
  > ⚠️ **该知识库后续没有接入工作流** —— 原因是嵌入服务计费受限。
  > 这是本项目的已知局限，见 [README §十一](../README.md#十一局限与后续)。

**结论**：链路能跑通了，但一次只能解析 JD，还没有"评估候选人"的能力。

## 阶段 2 ｜ 简历解析 + 打分节点

**目标**：让系统能对"一份 JD + 一份简历"给出分数。

- 新增 `简历解析` 节点，输出结构与 JD 解析对齐（技能 / 经历 / 教育 / 时间线）。
- 新增 `匹配打分` 节点。**这里做了一个关键决定：打分用纯 Python 代码节点，不用 LLM。**

  > **为什么**：分数是系统的核心输出，必须是**可复现、可测试、可解释**的。
  > LLM 输出的分数每次都可能不同，而且说不清怎么算出来的。
  > 所以职责分离——**模型只负责"读懂文本"，计算交给代码。**

- 权重定为 `硬性要求 50% + 关键词覆盖 30% + 经历完整度 20%`。

**结论**：能出分了，但分数"说不出理由"——报告只有一个数字。

## 阶段 3 ｜ 硬性要求改为语义判断

**问题**：第一版硬性要求用字符串匹配。简历写"本科"，JD 要求"大专及以上"——
字符串匹配判**不满足**（因为简历里没有"大专"两个字），这是错的。

**修法**：
- 硬性要求交给模型**逐条做语义判断**，并要求每条给出 `satisfied` 和 `evidence`（简历原文）。
- **保留字符串匹配作为兜底**，在输出里用 `hard_mode` 字段标注当前走的是哪条路径。
- 兜底路径存在的原因：模型偶发失败时不能让整条流水线崩掉，降级也要能出结果。

**实测**：同一份简历同一段 JD，字符串匹配给 `hard_score = 14`，语义判断给 `57`。

**结论**：准确率上来了，但新的问题出现了——有些条件**根本无法从简历核验**。

## 阶段 4 ｜ 报告生成节点

**目标**：把分数变成 HR 能读、能复核的东西。

- 新增 `报告生成` 节点，输出**六章节固定结构**的 Markdown 报告。
- **关键约束：报告节点"只组装不判断"。**
  分数、命中、缺口、硬性要求是否满足全部由上游算好，报告节点只负责排版成人话。

  > **为什么**：如果让报告节点"自己再看一遍简历、自己下结论"，
  > 就会出现**报告结论和 `score` 打架**，而且无法定位是哪一步错了。
  > **判断只做一次，组装可以多次。**

- 提示词里加了一条规则：**发现上游数据矛盾时不要自行修正，标注"数据待核实"。**

  > 这条规则在开发过程中**三次**抓到了真 bug。最有代表性的一次：
  > 报告里写"上游疑似命中字段为空，但风险提示里有 5 项，两处不一致"，
  > 查下去发现是报告节点的变量被粘坏了（截断成了两个花括号 `{{`）。
  > **如果模型当时"聪明"地帮我圆过去，这个 bug 就永远不会被发现。**

**结论**：输出可读了。但一跑评测，发现分数**不可比**。

## 阶段 5 ｜ ★ 分数可比性治理 + 测试用例设计

### 5.1 发现的问题：同一岗位，分数不可比

同一个岗位连跑 8 次，`JD解析` 节点**每次给出不同的关键词表**：

| | 结果 |
|---|---|
| 15 个出现过的关键词 | 只有 8 个是稳定的 |
| 打分分母 | 在 **38 ~ 58** 之间摆动（**摆幅 52%**） |
| 后果 | 候选人 A 用分母 43 量、候选人 B 用分母 40 量，**分数根本不可比** |

**第一反应是调提示词去"压"这个波动——但那是治标。**

追下去发现是**架构问题**：
岗位解析被放在了**每个候选人的执行路径**里重新生成，
而**岗位要求是岗位的属性，跟来的是谁没关系**。

### 5.2 修法：新增「岗位要求路由」节点

```
用户输入
  ├─ jd_text        （JD 原文）
  └─ jd_json_fixed  （固化好的岗位档案，可选）
        │
        ▼
      JD解析 ──→ 岗位要求路由 ──┬──→ 硬性要求判断 ──→ 匹配打分
                              └──────────────────→ 匹配打分
```

实现"**解析一次、固化成岗位档案、所有候选人复用**"。

**效果**：分母从 `38~58` 波动 → **恒定 44**，同一候选人 `keyword_score` 恒定，
档位标签稳定。

**额外收益**：固化前需要人工审阅，这就给了**修正模型输出**的机会。实测中修了两处：
- `招聘数据统计` → `招聘数据`（模型把动宾短语倒装了）
- 把 `猎头` / `RPO` 从计分关键词里删掉——它们在 JD 里是"**优先**"条件，加分项不该让候选人扣分

> 这也是真实 ATS 系统的做法：JD 录入一次 → 结构化 → 复用。

### 5.3 测试用例设计

设计了 **20 组边界用例**，覆盖 10 种简历类型 + 2 个 JD 边界：

完全匹配 / 技能缺失 / 信息残缺 / 跨专业 / 超长简历 / 英文简历 /
关键词堆砌 / 时间线冲突 / 实习不相关 / 同岗不同级 / 空输入 / 重复投递
／超短 JD（72 字）/ 超长 JD（1076 字）

**判据设计上的一个取舍**：以**行为期望**为主判据，分数期望只作参考。

> **为什么**：分数刻度是项目自己定的，拿自己定的刻度当标准答案，等于自己证明自己。
> 而"报告里是否出现关键词堆砌警告""证据栏有没有编造字段"是**可证伪的客观事实**。

**结论**：分数可比了，评测口径也定下来了。但评测跑起来之后，发现了最危险的一类错误。

## 阶段 6 ｜ 本地界面 + 三个"没有报错的 bug"

**目标**：把"只能自己在 Dify 后台跑"变成"打开一个网页就能用"。

- 用 **Python 标准库**（`http.server`）写了一个零依赖的本地界面，另附一个 Streamlit 版本。
  > 选标准库而非框架，是因为本项目代码**全部只用标准库**——
  > 这样任何 Python 环境都能直接跑，不用管 venv 和版本冲突。
- 界面支持从 `test/` 的用例清单里一键载入输入，方便跑评测。

### 三个"没有报错的 bug"（最重要的一段经历）

| # | 现象 | 真因 |
|---|---|---|
| 1 | 报告里写"上游疑似命中字段为空，但风险里有 5 项，两处不一致" | 报告节点的 `suspect` 变量在粘贴时被截断成 `{{` |
| 2 | 输入填错，系统给出 **56 分「待定，需人工复核」** | 打分代码里的 `else 60` 兜底默认值造出了**虚假分数** |
| 3 | 三个输入框填了文件路径，模型返回一堆"未说明" | 文档里"填 `data\jd\jd_01.txt`"有歧义（到底填内容还是填路径） |

**共同点：系统都在"正常工作"，只是结果错了。**

> 其中第 2 个是最危险的——它**不报错、不崩溃，输出一个看起来完全合理的评估结论**。
> 一个假阳性（放过不合格的人）比漏掉一个好人的代价大得多。

**统一应对思路**：

```
要么把操作自动化（不让人做精确操作），
要么让系统能识别出错误，并明确报出来。
```

修完之后，坏输入会明确返回：

```
score = 0
level = 数据不足，无法评分
risk  = ⚠️ 最常见的原因是把文件路径当内容填进了输入框 …
```

而不是一个像模像样的 56 分。

### 打分逻辑的 7 版迭代

每一版都是**被一个具体的真实问题驱动**的，完整表格见
[README §八](../README.md#八迭代记录)。其中最典型的一次：

一份技能栏堆了 32 个词、实习只写了一句"完成领导交办的其他事项"的简历，
只做字面匹配能拿到 **72 分「推荐进入面试」**。
修法是把简历拆成"**强证据区（做过）**"和"**弱证据区（声称会）**"、只对前者计分，
该简历降到 **30 分「暂不推荐」**，而正常简历几乎不受影响（86 → 88）。

**结论**：功能完整了。接下来是文档和开源。

## 复盘：这个项目里真正学到的东西

**不是"会用 Dify"，而是学会了怎么让 AI 的输出变得可信。**

| 学到的东西 | 具体体现在哪 |
|---|---|
| **把"判断"和"措辞"分开** | 打分用代码，报告节点只组装不判断 → 结论不会自相矛盾 |
| **必须给证据，不能只给结论** | 报告每条命中项都附简历原文 → HR 能独立复核 |
| **保守优先于好看** | 疑似命中不计分、数据不足直接拒绝评分 → 宁可少给分，不给假阳性 |
| **要主动暴露矛盾，不要自动"圆场"** | 报告节点被要求标注数据不一致 → 三次抓到真 bug |
| **区分"报错"和"静默出错"** | 三个最难查的 bug 全都不报错 → 统一改成"要么自动化，要么显式报错" |
| **上升一层看问题** | 分数波动一开始想在提示词层面压，实际上是架构问题 → 加路由节点解决 |
